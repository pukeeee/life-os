# `src/` — два чітко розділені світи

Щоб поєднати **Clean Architecture (бекенд)** і **Feature-Sliced Design (фронтенд)**
без плутанини, `src/` поділено навпіл:

## 1. `src/server/**` — бекенд (Clean Architecture + DDD)

Серверне ядро: bounded contexts, use cases, домен, інфраструктура, composition root.
Деталі — у `src/server/README.md`. **Імпортується лише в серверному коді.**

## 2. FSD-шари — фронтенд

Feature-Sliced Design. Залежності спрямовані лише **вниз** по шарах:

```
app  →  views  →  widgets  →  features  →  entities  →  shared
```

- **`shared/`** — переробне без бізнес-контексту (ui-kit, lib, конфіг).
- **`entities/`** — бізнес-сутності для UI (картка метрики, її view-модель).
- **`features/`** — інтерактивні дії користувача (залогувати метрику) + їхні
  **Server Actions** (`api/`), що викликають use cases з `src/server`.
- **`widgets/`** — самодостатні композитні блоки (огляд доби).
- **`views/`** — складання сторінок зі шарів (FSD «pages», перейменовано, щоб не
  конфліктувати з роутингом Next).
- **`app/`** (FSD) — глобальні провайдери/обгортки (не плутати з Next `app/`).

Маршрутизація Next.js лишається в кореневому `app/` і робить лише одне:
імпортує відповідний `view`.

### Межа фронтенд ↔ бекенд
Єдиний канал — **Server Actions** у `features/*/api`. Вони викликають
`getContainer()` і повертають **прості серіалізовні DTO**. Клієнтські компоненти
ніколи не імпортують доменні класи (лише type-only view-моделі з `entities`).
